## Goal
Design Phase 4 of PRD-v2 (`docs/PRD-v2.md` §Phase 4, ~lines 109–116; `docs/v2/PLAN.md` §Phase 4). The headline need comes from Phase 3: alerts and history only work while Live runs, and **Live stops when the panel closes** (`docs/v2/PHASE-3-REPORT.md`; `handoffs/merged/2026-10-28-1215-v2-3c-alert-policies.md`). **No source code changes.**

**Done when** these exist, in the shape of the existing ADRs (`docs/v2/ADR-0005-history-store.md`, `docs/v2/ADR-0006-force-quit.md`):
1. `docs/v2/ADR-0008-background-helper.md`, which decides:
   - **Shape:** a LaunchAgent helper (an `SMAppService` agent bundled in the app) vs. a login-item app vs. keeping the main app alive with no panel. Say what each costs in signing, notarization, sandbox/entitlements (the v1 Phase 0 choice: read `App/*.entitlements` and `docs/FEASIBILITY.md`), and in uninstall clarity.
   - **IPC:** XPC (Mach service) between app and helper, the message set (typed, versioned), and how the app reads live ticks, alerts and explanations from the helper. ADR-0003 chose "no local server": keep it.
   - **What runs in the helper:** sampling, `AlertEvaluator`, `ConcurrencyRules`, `HistoryRecorder`. What stays in the app: all UI, and **every stop/force-quit/container-stop action**. Say whether the helper may ever signal (ADR-0006 "Revisit when" says the ledger and the 5 s/60 s rules must move with any signalling; recommend the helper never signals).
   - **Opt-in and lifecycle:** "Run in the background" (off by default, per the plan's rule), launch at login, pause/quit, and clear uninstall (what's left behind and how to remove it).
   - **Overhead budget:** CPU at idle and during an incident, memory, battery-aware defaults; measured the way `docs/PERFORMANCE.md` measures.
   - **Security review** section, like `docs/v2/SECURITY-REVIEW-3d.md`: XPC peer validation (code-signing requirement of the caller), what the helper exposes, file permissions, and what happens if the app is replaced or downgraded.
   - **Options considered**, then **Build briefs**: one per phase, each with exact files, the pattern to copy, done + its proving command, and may/must-not-touch (as ADR-0006/0007 did).
2. `docs/v2/PHASE-4-PLAN.md`: the remaining Phase 4 items, with a short design and the build briefs for each, sequenced after the helper:
   - **adaptive sampling** (slow when idle, fast during an incident; battery-aware)
   - **watchlists**: per-project CPU/memory/concurrency warning policies, built on `AlertPolicy` (alerts only; enforcement is future/opt-in)
   - **incident export**: a privacy-redacted incident report from the timeline + explanations + action log, reusing `Redactor`
   - **structured local logs** and **crash recovery**
   - **Jarvis integration** through the existing stdio MCP server (read-only tools: e.g. live explanations and recent alerts, only if the helper runs)
   - say which items need product decisions
3. Questions that need the owner go in a `status: blocked` first handoff, each with your recommendation, e.g.:
   - Is the background helper in v2.0 or v2.1?
   - Should alerts from the helper respect Focus modes?
