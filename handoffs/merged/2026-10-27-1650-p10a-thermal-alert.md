## What the user asked
An opt-in alert, off by default. When macOS's thermal state rises to serious or critical, HeatLens
runs one normal scan and posts a notification naming the top culprit. Clicking the notification
opens the panel on those results. At most one alert every 30 minutes, and the only trigger is
`thermalStateDidChangeNotification`: no polling and no timers.

## What changed
- **Core policy** (`ThermalAlertPolicy`, pure and tested):
  - `shouldScan` is true only on a rise into serious or critical, with the setting on, no scan
    running, and at least 30:00 since the last alert. It is false at 29:59. `unavailable` counts as
    nominal.
  - `summary(for: ScanResult, exclusions:thermalState:homeDirectory:)` returns the title "Your Mac
    is running hot". The body names the top visible `highCPU` finding's group as label, then project
    folder name, then group CPU, e.g. `vitest in Tests · 96% CPU`. With no such finding it says "No
    single process stands out. macOS reports serious|critical thermal pressure."
  - Redaction: words in the label that look like paths are cut to their last component, and the
    user name is dropped. The project is left out when it would be the home folder or `/`. The
    label is capped at 40 characters and the project at 32, so the body stays under about 110.
  - The brief's `summary(for: ScanReport)` took a `ScanResult` instead, because `ScanReport` is an
    App-only type. The App builds one from the report's snapshot, groups and findings.
- **Core `ExclusionFilter`**: a port of ResultsView's private `visibleFindings` and
  `matchesExclusion`, with the same semantics: case-insensitive process names, and `~`-expanded,
  standardized project prefixes matched on a path boundary. A finding is hidden only when every
  process it affects is excluded. ResultsView is not touched; pointing it at this filter is left
  for Jarvis.
- **App `ThermalAlertService`**:
  - It holds the thermal observer only while the setting is on. It follows the setting with
    `withObservationTracking`, so toggling it adds or removes the observer at once.
  - On a qualifying rise it records `lastAlert` (in memory only), calls `model.startScan(onFinish:)`,
    and posts one notification (`dev.heatlens.thermal-alert`, which replaces any earlier one) only
    when the scan returns results. Failed or cancelled scans post nothing.
  - Clicking the notification calls `StatusPanelController.show()`. Banners show even while
    HeatLens is active, through `willPresent`.
- **ScanModel**: `startScan(duration:onFinish:)`. The handler is called exactly once, with the
  report, or nil on failure, `alreadyRunning` or cancel. Generation and cancel logic are unchanged,
  and existing call sites compile as they were.
- **StatusPanel**: one public `show()` that calls `open()`.
- **Settings**: `thermalAlertsEnabled` is stored in UserDefaults, default false. Settings has the
  toggle "Alert me when my Mac runs hot" with the caption from the brief. Turning it on requests
  `.alert` authorization. If permission is denied, the row shows "Notifications are off for
  HeatLens" with an "Open System Settings" button (`x-apple.systempreferences:com.apple.Notifications-Settings.extension?id=<bundle id>`).
- **Debug trigger**: `-HeatLensSimulateThermal serious|critical` is `#if DEBUG` only. Three
  seconds after launch it feeds one rise from nominal through the same policy, so the toggle still
  gates it.
- **Docs**:
  - README: one bullet under Privacy. Status already has 10b's uncommitted line, so this one went
    elsewhere to keep the hunks separate.
  - `docs/PERFORMANCE.md`: section 1, item 5. Idle cost is unchanged: one observer, no timer, and
    no observer at all when the setting is off.

Judgment calls (none needed a user ruling):
- `lastAlert` is set when the alert's scan starts, not when the notification posts. A scan that
  fails still uses up the 30 minutes, which caps scans as well as notifications.
- `lastAlert` lives in memory, so a relaunch resets the cooldown. HeatLens stores no history.
- The "culprit" is the top visible finding of kind `highCPU`. Stale servers, detached workers,
  WindowServer and kernel_task are not named as culprits.
- If the setting is on but permission was never asked (for example, set with `defaults`), the
  service asks once before posting.
