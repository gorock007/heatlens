## What changed
- **Settings → "Offer Force Quit when a process ignores a stop request"**
  - Key `forceQuitEnabled`, default false, the same `didSet` pattern as `dockerEnabled`.
  - It sits in a new `ActionsSection` ("Actions") right after the monitoring sources, with the ADR's caption.
- **`ProcessStopping`** gains two members:
  - `forceQuit(_:context:)`;
  - `stopRequestedAt(_:)`, which returns the ledger's SIGTERM time. The countdown and the 60 s
    expiry use the engine's own time, not a UI guess.

  `requestStop` now takes `context: ActionContext`.
  - `TerminatorStopService` owns the one `StopLedger`. The struct is copied, but the actor is
    shared, and `HeatLensApp` creates one service. That service is passed to both the single and
    the batch flows.
  - It takes `forceQuitAllowed: @MainActor @Sendable () -> Bool`, which reads
    `settings.forceQuitEnabled`. When it returns false, `forceQuit` returns
    `.denied("Force Quit is off in Settings")` before touching the engine (ADR test 10, by code read).
  - `FixtureStopService` returns `.stillRunning` for PID 23140 (a portfolio-demo leftover) and
    `.stopped` on force quit, so fixture mode and previews show the offer.
  - `LiveNoStopService` denies `forceQuit`, and its `stopRequestedAt` returns nil.
- **`StopWording.message(for:pid:signal:forceQuitOffered:)`** and `status(for:signal:)`:
  - SIGKILL sentences, and the row status "force quit".
  - A still-running result reads the decision-1 text when the switch is off, and "You can force
    quit it below." when it's on.
  - The progress captions now say "never force-quits on its own".
- **`StopFlowView` (ResultsView.swift):** a `.stillRunning` result shows **Force quit…** when the
  switch is on, with "Stop request sent N s ago", updated every second.
  - At 60 s (`ProcessTerminator.offerLifetime`) the button disables and reads "Too long since the
    stop request; request a stop again."
  - Pressing it swaps the sheet to `ForceQuitFlowView`. That is a separate step, never the SIGTERM step.
- **`ForceQuitFlowView`** (new, shared by both call sites) has phases `.forceQuitConfirmation`,
  `.forceQuitting` and `.forceQuitOutcome`.
  - It shows the process name and PID, the project, the uptime, and "Stop request sent N s ago,
    ignored".
  - It shows the decision-4 warning and the child-process line.
  - **Cancel** is the default (Return). **Force Quit** is destructive, has no shortcut, and is
    disabled at 60 s.
  - It has the `guard case` double-dispatch guard, and `interactiveDismissDisabled` while the
    signal is in flight.
  - Grace and expiry come from the engine constants (`minimumGraceAfterStop`, `offerLifetime`);
    no hard-coded 5 or 60.
  - Cancel in the single flow goes back to the "still running" result. In the batch flow it closes
    the confirmation.
- **`BatchStopFlowView`:** after the run finishes, each `.finished(.stillRunning)` row gets its own
  small **Force quit…** button with the same countdown.
  - The button opens `ForceQuitFlowView` for that row only, through `.sheet(item: $forceQuitTarget)`.
  - The row then reads "force quit", or the refusal reason. There is no bulk control.
  - With the switch off, the row says the decision-1 text instead.
- **`ActionContext` on every call:**
  - origin `processDetail` from process detail;
  - `leftoverCard` from any finding card (see note 1);
  - `batchStop` for batch SIGTERMs and per-row force quits.

  `processName` and `projectName` (folder name only) are passed too. `confirmedAt` is the moment
  the confirming button was pressed; one shared time for a batch.
- **README:** "SIGTERM only" became "SIGTERM only by default", plus two lines that name the switch.
  `docs/LIMITATIONS.md` has no such line, so it's untouched. README line 4 ("read-only …
  diagnostic app") doesn't claim SIGTERM-only, so I left it.

## Click-through for the user
1. `scripts/run-app.sh`
2. In Terminal, `cd` into a project folder (a Git repo) and run `bash -c 'trap "" TERM; exec sleep 600'`.
   Leave it running. Only ever signal this process.
3. **Scan now.** Open that bash/sleep process → **Request stop** → **Send SIGTERM**.
   - Expect: "didn't exit. HeatLens does not force-quit unless you turn that on in Settings;
     Activity Monitor can also stop it."
   - There is no Force quit button.
4. Settings → **Actions** → turn on "Offer Force Quit when a process ignores a stop request" → Done.
5. Scan now → same process → Request stop → Send SIGTERM.
   - Expect: "You can force quit it below.", a **Force quit…** button, and "Stop request sent N s
     ago" counting up.
6. **Force quit…**
   - The second sheet names the process, PID, project, uptime and stop-request age, and shows the
     SIGKILL warning.
   - Return = Cancel, which takes you back to the result. Press Force quit… again → **Force Quit**.
   - "Waiting…" lasts until at least 5 s after the SIGTERM.
   - Then: "Process PID … was force quit (SIGKILL)." The shell is gone in Activity Monitor.
7. Expiry: repeat to the result step and wait past 60 s. The button disables with "Too long since
   the stop request; request a stop again."
8. Batch: start two such processes in the same project folder (both must show as leftovers, which
   for detached ones means PPID 1, e.g. `nohup … &` then close the terminal tab). Scan →
   **Stop leftovers (2)…** → Stop selected.
   - Each "still running" row has its own Force quit… button; there is no "force quit all".
   - Force quit one: its row reads "force quit", and the other row keeps its own button.
9. Faster UI check without real processes: in a Debug build launched with `-HeatLensFixtures YES`,
   PID 23140 (portfolio-demo) always comes back "still running".
